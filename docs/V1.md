# neoKernel Version 1

Version 1 marks the project as it stood on September 22, 2026. The documentation covers the automated research loop and the engine results that followed. It identifies assisted engine changes separately from automatic harness keeps.

The historical harness snapshot has source anchor `aa662a35a155c333b7c8965061d38574db68cfaf`. Later scored engine changes have their own commits. Version 1 is a project milestone, not a newly measured engine freeze. No new GPU evaluation was performed for this documentation.

## Read the documentation

Open [index.html](index.html), or serve the site from the repository root:

```powershell
python -m http.server 8765 --bind 127.0.0.1 --directory docs
```

Visit `http://127.0.0.1:8765`. The site uses static HTML, CSS and JavaScript. It has no build step. The 3D model uses CSS transforms. The diagrams and controls do not call the harness or start remote jobs. Fonts load from Google Fonts, with local fallbacks.

The 3D model supports pointer dragging and arrow keys. The layer slider and reset button also work from a keyboard. Motion starts only on request. Reduced motion switches the cycle player to a single-step control.

## Later verification

A later test session reported that a speculative kernel API mismatch caused two errors in ten L4 tests. After restoration, all ten passed. A three-sample H100 benchmark on the public workloads passed its recorded gates. Its TTFT ratios were 0.47 to 0.65, TPOT ratios 0.19 to 0.27, spread at most 0.04 and memory 13 percent of the device.

One automated proposal then passed the guard and ten L4 unit tests with no repairs. It failed the H100 benchmark and was reverted. That shows the rejection path working, not an automated performance keep. Manual investigation found a shared draft table that changed tokens across repeated calls and a grouped SDPA path with a 7.0-logit gap at batch 32. The latter was removed in favor of the Triton path, which measured 0.25 in that comparison.

After those engine fixes, the engine on main passed all six local H100 workloads in a five-sample run at 731.0 local tok/s. This is a local result on different workloads, not another point on the external score line. The native reference's worst self-replay margin in twelve observations was 0.5 logits. The harness now uses a separate 0.75-logit native noise floor and keeps the candidate's 2.0-logit contract limit.

Trial 39's earlier 4.0-logit local failure did not recur in one L4 check and four H100 benches covering thirteen samples per workload. The earlier failure remains unexplained. The later session's raw GPU outputs are not included in the checked-in historical export.

## How the loop works

1. Measure the current engine as a baseline.
2. Give the proposal model the current source, profile, recent history and allowed playbook.
3. Validate the complete replacement files and run the source guard.
4. Run unit tests on L4. Allow up to two repairs from the same model.
5. Run public correctness checks before three H100 samples per selected workload.
6. Keep only if every local gate passes, aggregate improvement exceeds 1% and no workload regresses more than 3%.
7. Save the experiment. Restore a rejected candidate or commit and merge a passing keep locally.

The current implementation is authoritative where earlier notes describe a different stage. In particular, `transaction.py` now commits and merges local keeps. It never pushes. The per-workload regression condition was added after trial 37.

### Record integrity

A log entry cannot record a keep that its own attached evidence contradicts. `append_log` refuses a keep when any workload in the result reports a failed gate, or when the result is not eligible. The rule is contradiction rather than proof, so an entry carrying no measured workloads still records a decision taken elsewhere.

This was added after trial 39, which was written as a keep while carrying a failed correctness gate on public-2, because an external score was allowed to outrank the local gate. Every later trial then measured against a baseline the record itself marks as wrong. The historical row is preserved as it was written.

A run that dies before producing a result now leaves a record of the attempt under `results/runs/` marked failed and ineligible. Without it the newest file in that directory was the previous run and could be read as the current one.

Source files: [loop.py](../neokernel/loop.py), [judge.py](../neokernel/judge.py), [transaction.py](../neokernel/transaction.py), [accounting.py](../neokernel/accounting.py) and [schema.py](../neokernel/schema.py).

## Evaluation

The target is the pinned Qwen3 4B checkpoint in BF16. The local judge measures complete generation, replays candidate tokens with an independent native model and checks each token against the native argmax with a 2.0 logit margin.

Every run draws its sample prompts from one recorded seed, saved on the result and printed as `--prompt-seed`. The candidate and the native reference are measured on the same prompts, so a paired comparison is paired in fact, and a correctness result can be replayed instead of retold. Each replay also records the worst margin it saw whether or not it passed, so an engine sitting close to the limit is visible before it fails.

The native reference is held to its own separate budget of 0.75 logits, replayed against itself. That number is a measurement floor rather than a verdict on any candidate, and it is calibrated: across two seeded five-sample runs of all six workloads, native's worst self-replay margin was 0.5, and the engine contract documents this noise as up to 0.75. When native exceeds it the run has left the regime the 2.0 candidate margin was calibrated in, so the affected workload is reported as a harness error and retried. It is never charged to the candidate. Reusing the candidate's 2.0 for this check let the reference sit far outside its own noise floor and only complain when it happened to cross the candidate's gate.

Dryft is the external evaluator. Its hidden workloads determine the official score. The local harness uses public shapes and guessed proxy shapes, so local aggregate throughput and official throughput are not interchangeable. The local latency ratio limit is 1.05. The official limit in the included contract is 1.10.

The local runner is process isolation, not a hardened security sandbox. Parent and child share an operating system identity. Memory is based on the child's allocator report.

See [the engine contract](../QWEN_ENGINE_CONTRACT.md) and [local judge](../neokernel/judge.py) for the complete rules.

## Future work

Version 2 is planned work. Version 1 currently uses GLM through Baseten and GPU jobs on Modal. The aim is an API provider agnostic and GPU provider agnostic harness. Check the [Future work section](index.html#future) for more details.

### Multiple agent swarms

Run multiple swarms in parallel, each exploring a different hypothesis. Give candidates isolated workspaces and budgets. Share measured findings and failed attempts. Reserve GPUs for timing runs and re-evaluate combined changes through an independent judge. Check the [Future work section](index.html#future-swarms) for more details.

### API and GPU provider independence

Separate model API adapters from GPU execution backends. Keep a common proposal and result format while recording each provider's usage and each machine's environment. A new GPU architecture still needs compatible kernels and correctness checks. Check the [Future work section](index.html#future-api) for more details.

### Python package

Build toward an installable package with a Python API, CLI, provider adapters and reproducible experiment reports. Users would provide an engine, reference, workloads and budget. This is a planned interface, not a published package. Check the [Future work section](index.html#future-package) for more details.

### Research directions

Investigate parallel search with shared memory, compiler autotuning, broader held-out evaluation and stronger Anti Reward Hacking protections. Compare search strategies under fixed budgets. These are proposed directions, not measured Version 1 outcomes. Check the [Future work section](index.html#future-research) for more details.
